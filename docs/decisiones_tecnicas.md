# Decisiones técnicas

Registro del proyecto ISTEA Laboratorio de Minería de Datos. Recoge el diseño de la Etapa 1A, la evidencia local de la Etapa 1B y las decisiones aprobadas en la Etapa 1C.

## DT-001 · Datos y preprocesamiento · 2026-11-25

- **Contexto.** El paquete del profesor incluye datos históricos, producción simulada y un lote de scoring. Solo el histórico contiene la etiqueta `Churn`.
- **Decisión adoptada.** Usar el histórico para entrenamiento y evaluación, reservar producción simulada para monitoreo y excluir `customerID` de los predictores. El diseño reutiliza el pipeline existente para tratar los faltantes y ajustar las transformaciones dentro de cada fold.
- **Criterio de evaluación.** El pipeline declara el histórico como entrada y las pruebas verifican la exclusión del identificador y el ajuste del preprocesamiento dentro de cada fold.
- **Resultado observado.** La Etapa 0 confirmó igualdad de SHA-256 entre el histórico del profesor y el CSV local. En la Etapa 1B los seis candidatos compartieron las mismas particiones de validación y el preprocesador se ajustó dentro de cada fold.
- **Evidencia.** [Puntero DVC del histórico](../data/raw/customer_churn_historical.csv.dvc), [partición y predictores](../src/training/train.py) y [preprocesamiento](../src/features/build_preprocessor.py).
- **Limitación.** La evaluación histórica no mide desempeño en producción. El lote de producción simulada carece de etiquetas.

## DT-002 · Comparación y selección · 2026-11-25

- **Contexto.** El código de la segunda entrega compara tres modelos sobre el mismo holdout y selecciona Logistic Regression por nombre.
- **Hipótesis inicial.** Ponderar la clase minoritaria podría reducir los falsos negativos. La regularización puede modificar el equilibrio entre recall y precision.
- **Decisión adoptada.** Comparar seis configuraciones de las familias existentes en cinco folds estratificados con la misma semilla y particiones. Mantener el split 80/20 con semilla 42 y la regla de clasificación de `predict()`. Seleccionar por recall medio entre candidatos con precision media de al menos 0,50, con desempate por F1 y simplicidad. Reajustar al ganador sobre todo el entrenamiento y evaluarlo en el holdout.
- **Criterio de evaluación.** Comparar accuracy, precision, recall, F1, ROC-AUC y matrices de confusión con los mismos folds. Justificar la elección y sus falsos negativos antes de consultar el test.
- **Resultado observado.** La regresión logística con `class_weight="balanced"` y `C=1` obtuvo el mayor recall medio entre los candidatos elegibles. Sobre el mismo holdout de `entrega-2`, el recall pasó de 45,16 % a 72,31 %. Los falsos negativos bajaron de 204 a 103 y los falsos positivos subieron de 85 a 290.
- **Ratificación en la Etapa 1C.** Se acepta la precision de 0,4812 del holdout. El piso de 0,50 se aplica a la media de validación cruzada. Se conserva la configuración seleccionada y la regla de selección aprobada. El holdout se usa exclusivamente para informar el desempeño final.
- **Evidencia.** Experimento local `ISTEA_Churn`, run ganador `5b521ee4632742528e0f6e69edc14350` y run de holdout `d203aaf89f8a4c558c3616a1671c1edb`. Los runs de candidatos contienen `validation.json`. El run final contiene `holdout_confusion_matrix.json`. [Parámetros](../params.yaml) y [pruebas](../tests/test_training.py).
- **Ejecución definitiva · 2026-11-25.** El ganador y las métricas de validación y holdout coincidieron con la Etapa 1B. Se verificaron cinco folds únicos por candidato. El baseline conserva registros repetidos de los mismos pasos en el mismo run debido a la reanudación. [Validación del ganador](https://dagshub.com/yochelo/ISTEA-Laboratorio-Mineria-Datos.mlflow/#/experiments/0/runs/eae4f71c2f884254ada305938f0b8417) · [Run final y matriz de holdout](https://dagshub.com/yochelo/ISTEA-Laboratorio-Mineria-Datos.mlflow/#/experiments/0/runs/778771c7af9e40dcb771cc5becfc9142)
- **Limitaciones.** El holdout ya se utilizó en la entrega anterior. Permite comparar ambas versiones, con valor limitado como evaluación inédita. La ausencia de costos comerciales reales impide establecer una configuración económicamente óptima. La ponderación modifica la función objetivo y puede afectar la interpretación de las probabilidades como riesgo absoluto. La justificación de los niveles de riesgo en serving deberá considerar esta limitación y la calibración del modelo.

Usar Git para identificar la revisión base y MLflow para conservar el diff de entrenamiento mientras el código esté sin commit. DVC versiona datos y salidas. El nombre aprobado para el futuro registro es `ISTEA_Churn`. La publicación requiere autorización posterior.
- **Criterio de evaluación.** El estado DVC queda limpio tras la ejecución. La versión registrada resuelve al run y al commit esperados. El archivo de serving recuperado desde DVC y el adjunto de la versión registrada comparten SHA-256.
- **Resultado observado.** DVC regeneró el lock y confirmó que el stage quedó al día. El archivo adjunto al modelo en MLflow local y el artefacto DVC coincidieron byte a byte. Se preservaron los objetos de la segunda entrega.

Un commit posterior incorpora el `dvc.lock` regenerado y referencia el SHA de entrenamiento y el run final. Los binarios y las métricas se conservan como objetos DVC.

## DT-004 · Identidad del modelo servido · 2026-11-25

- **Contexto.** FastAPI carga un archivo local y expone una versión fija. Sustituir el archivo puede mantener la misma versión declarada.
- **Decisión adoptada.** Conservar la carga local. Un manifiesto declara la versión exacta del Registry, el run, el commit de entrenamiento y el SHA-256 esperado. El loader verifica los mismos bytes que deserializa y comprueba interfaz, clases y features. La API publica la identidad `ISTEA_Churn/1` desde el manifiesto.
- **Criterio de evaluación.** El artefacto aprobado reproduce la predicción directa. Un archivo con digest distinto se rechaza antes de deserializarse. Un artefacto ausente, corrupto o incompatible deja el HTTP operativo y devuelve 503 en readiness y predicción válida.
- **Resultado observado.** La prueba de integración reprodujo etiqueta y probabilidad del pipeline directo. Las pruebas de fallo confirmaron 503 sin cargar otro modelo. Un fallo inesperado de inferencia produjo 500 genérico y se pudo correlacionar con el identificador de solicitud.
- **Evidencia.** [Manifiesto](../app/model_manifest.json), [carga del modelo](../app/model_loader.py), [ciclo de vida y rutas](../app/main.py) y [pruebas](../tests/test_api.py).
- **Limitaciones.** Readiness refleja la verificación de carga durante el arranque. Cada cambio de modelo exige actualizar de forma coordinada el artefacto y su manifiesto. La identidad se verificó en FastAPI local y posteriormente dentro del contenedor de la Etapa 3A.

## DT-005 · Contrato de entrada de FastAPI · 2026-11-25

- **Contexto.** La segunda entrega aceptaba categorías desconocidas, coerciones numéricas y combinaciones incompatibles de servicios. La Etapa 2A contrastó el diccionario, el esquema y los ejemplos del profesor con los CSV originales.
- **Decisión adoptada.** Usar Pydantic v2 en modo estricto, con dominios explícitos y campos adicionales prohibidos. Exigir `SeniorCitizen` entero entre 0 y 1, `tenure` entero entre 0 y 72 y cargos finitos. El cargo mensual debe ser positivo. El total admite cero, omisión o `null`, y el pipeline conserva su imputación. Las cuatro formas de pago se tomaron de los CSV originales, ya que el diccionario solo indica la cantidad.
- **Fundamento.** Los tres CSV cumplen las correspondencias entre telefonía y líneas, y entre ausencia de internet y los seis servicios asociados. El contrato comprueba ambas direcciones de esas correspondencias. El rango aproximado de cargos mensuales queda como referencia descriptiva.
- **Criterio de evaluación.** Los ejemplos oficiales producen HTTP 200 y 422 según corresponda. Tipos, dominios y combinaciones inválidas producen 422 antes de inferencia, incluso cuando el decodificador recibe números no finitos. OpenAPI expone los dominios y límites y describe la coherencia entre servicios.
- **Resultado observado.** Validaron las 9.643 filas originales tras proyectarlas a las features de entrada y representar los faltantes como `null`. Los ejemplos oficiales conservaron sus resultados esperados y la suite completa aprobó. Para los errores de validación con valores no finitos, la respuesta conserva el formato `detail` y representa esos valores como texto para poder serializar el HTTP 422.
- **Evidencia.** [Esquema Pydantic](../app/schemas.py), [respuesta de errores de validación](../app/main.py) y [pruebas HTTP y OpenAPI](../tests/test_input_validation.py).
- **Limitación.** OpenAPI describe las reglas entre campos en texto. La aplicación las ejecuta mediante el validador Pydantic. La verificación por CSV fue una comprobación del contrato, sin ajustar el modelo ni utilizar producción simulada para selección.

## DT-006 · Estados HTTP y niveles de riesgo · 2026-11-25

- **Decisión adoptada.** Usar `/live` para liveness, `/ready` para disponibilidad del modelo y `/health` para estado general e identidad. Usar un UUID por solicitud y devolverlo en la cabecera `X-Request-ID` y en el cuerpo de las predicciones exitosas. Conservar el error 422 y separar indisponibilidad de modelo (503) de fallos inesperados de inferencia (500).
- **Criterio de evaluación.** Comprobar los estados HTTP, la correspondencia del UUID, la búsqueda de la clase `Yes`, la validez de las probabilidades y los límites de riesgo.
- **Resultado observado.** Sobre el holdout histórico, se asignaron 584 registros a LOW (38 churn), 523 a MEDIUM (149 churn) y 302 a HIGH (185 churn). Las pruebas confirmaron los bordes 0,30 y 0,70 y el rechazo de probabilidades inválidas mediante un 500 genérico.
- **Limitación.** Los cortes 0,30 y 0,70 son ilustrativos para priorización. Las tasas observadas por nivel describen ese holdout. La ponderación de clases modifica el ajuste y las probabilidades del modelo carecen de calibración verificada como riesgo absoluto.
- **Evidencia.** [Inferencia y cortes](../app/inference.py), [respuestas HTTP](../app/main.py) y [pruebas de límites y fallos](../tests/test_api.py).

## DT-007 · Alcance y aislamiento de pytest · 2026-11-25

- **Contexto.** El ejecutable `pytest -q` fallaba al importar `app` y `src` desde la raíz. Algunas pruebas de contrato cargaban el artefacto real aunque su comportamiento podía verificarse con datos pequeños y un doble de modelo.
- **Decisión adoptada.** Configurar la ruta de importación y el marcador `dvc` con pytest. Centralizar el ejemplo válido en `sample_customer` y mantener `TestClient` dentro del contexto de cada prueba. Los casos de validación y fallos pueden utilizar dobles o archivos de prueba temporales. El smoke test conserva el modelo real.
- **Resultado observado.** La suite completa aprobó en el orden habitual y en el orden inverso de los casos recolectados. Los grupos `-m dvc` y `-m "not dvc"` aprobaron en ejecuciones separadas. El segundo se ejecutó en una copia sin CSV histórico, modelo ni caché DVC. El smoke test también aprobó de forma aislada. Compara la etiqueta y la probabilidad de `Yes` por HTTP con las del pipeline directo y verifica identidad y UUID.
- **Evidencia.** [Configuración pytest](../pytest.ini), [fixtures](../tests/conftest.py), [esquema de datos](../tests/test_load_data.py), [imputación](../tests/test_preprocessor.py), [modelo](../tests/test_model.py), [API](../tests/test_api.py) y [validación parametrizada](../tests/test_input_validation.py).
- **Limitación.** Starlette 1.10.0 intenta usar `httpx2` y emite una advertencia cuando usa el `httpx` 0.28.1 instalado. Adoptar `httpx2` requiere revisar las dependencias. La advertencia permanece visible. El smoke test usa ASGI en proceso mediante `TestClient`. La ejecución en contenedor se verificará por separado.

## DT-008 · Imagen de serving · 2026-11-26

- **Contexto.** El Dockerfile de la segunda entrega instalaba también herramientas de entrenamiento y pruebas. La imagen definitiva necesita FastAPI, el manifiesto y el pipeline local aprobado.
- **Decisión adoptada.** Conservar un Dockerfile de una sola etapa con Python oficial 3.11.9 slim por digest, dependencias de serving fijadas, usuario sin privilegios y healthcheck sobre `/ready`. Limitar el contexto a los archivos que requiere la imagen. El modelo se incorpora desde el checkout tras recuperarlo por DVC.
- **Criterio de evaluación.** La imagen arranca en Linux, verifica el hash del modelo y responde correctamente a los ejemplos oficiales. La predicción debe coincidir con el pipeline local y funcionar también con la red deshabilitada.
- **Resultado observado.** La imagen local `istea-churn-api:etapa-3a-modelo-1` quedó saludable. Las rutas de salud, documentación y predicción válida devolvieron 200. La solicitud inválida devolvió 422. La identidad y el UUID coincidieron con el contrato, y la diferencia de probabilidad respecto del pipeline local fue cero. El `joblib` conservó el SHA-256 aprobado. Una segunda ejecución con `--network none`, sin credenciales ni montajes, también predijo correctamente.
- **Evidencia.** [Dockerfile](../Dockerfile), [contexto de construcción](../.dockerignore), [dependencias de serving](../requirements-serving.txt) e ID de imagen `sha256:10b1f8ae1fcfdbf382d231c172ed92d7d9eab9b7fc17cf2526e7e903f1cbc522`.
- **Limitaciones.** Se verificó Linux AMD64 en Docker Desktop. Construir desde un checkout nuevo requiere recuperar primero el modelo y disponer de la imagen base y los paquetes. La prueba sin red cubrió el arranque y la predicción del servicio.

## DT-009 · Arranque declarativo con Compose · 2026-11-26

- **Decisión adoptada.** Mantener un único servicio `churn-api` con la imagen aprobada para `ISTEA_Churn/1`, la red implícita, el puerto histórico limitado a `127.0.0.1:8001` y `restart: unless-stopped`. El healthcheck se hereda del Dockerfile.
- **Resultado observado.** `docker compose config` resolvió la configuración esperada. El primer arranque llegó a `healthy`. Los endpoints de salud y Swagger respondieron 200. La predicción válida coincidió con el pipeline local, incluida la identidad y la correspondencia del UUID con la cabecera. El ejemplo inválido devolvió 422. Tras `down`, el segundo arranque reutilizó el mismo ID de imagen sin build y volvió a quedar saludable.
- **Alcance.** La verificación se hizo en Docker Desktop desde el host local. Al finalizar se retiraron el contenedor y la red propia del proyecto. [Configuración Compose](../compose.yaml)

## DT-010 · Logs y métricas de inferencia · 2026-11-26

- **Decisión adoptada.** Emitir eventos JSON por stdout con `logging` y reutilizar el UUID de la solicitud. Conservar `tenure`, `Contract` y `MonthlyCharges` en las predicciones exitosas porque permiten observar cambios de permanencia, modalidad contractual y cargo. Los rechazos se registran con su código y correlación, sin copiar el payload. Las etiquetas reales posteriores quedan fuera de este flujo.
- **Instrumentación.** Exponer `/metrics` con `prometheus_client.make_asgi_app`. Contar respuestas por ruta declarada y código HTTP mediante el middleware existente. Agrupar rutas desconocidas. Contar predicciones exitosas por versión y observar su score. La latencia mide cada intento que llega al código de inferencia, incluidos los fallidos.
- **Resultado observado.** Con Uvicorn, la predicción válida de `ISTEA_Churn/1` sumó una predicción, un score y una observación de latencia. La solicitud incorrecta incrementó exclusivamente el contador 422 de predicción. Los UUID del log y de las respuestas HTTP coincidieron. Las pruebas confirmaron también los contadores HTTP de 503 y 500 y la preservación del resultado predictivo.
- **Evidencia.** [Instrumentación en FastAPI](../app/main.py), [pruebas de métricas y logs](../tests/test_instrumentation.py) y [versión fijada de serving](../requirements-serving.txt).
- **Limitaciones.** Los contadores e histogramas residen en el proceso y se reinician con él. La verificación se hizo con un proceso Uvicorn local. El montaje ASGI puede redirigir `/metrics` a `/metrics/`. La recolección, persistencia y visualización quedan para etapas posteriores.

## DT-011 · Recolección de métricas con Prometheus · 2026-11-26

- **Decisión adoptada.** Ejecutar Prometheus 3.5.0 mediante Compose y recolectar el job `ml-api` desde `churn-api:8000/metrics` cada cinco segundos. La red implícita resuelve el nombre del servicio. La configuración se monta en solo lectura y el volumen nombrado conserva las series.
- **Resultado observado.** El target quedó `UP` y dos scrapes consecutivos estuvieron separados por cinco segundos. Se conservó `/metrics` porque Prometheus sigue la redirección HTTP 307. El tráfico de laboratorio produjo seis predicciones exitosas y tres rechazos 422. Una consulta al mismo instante histórico conservó el valor seis tras recrear Prometheus.
- **Consultas.** Se verificaron `rate(ml_predictions_total[5m])`, `sum by (model_version) (rate(ml_predictions_total[5m]))`, `histogram_quantile(0.95, rate(ml_prediction_latency_seconds_bucket[5m]))` y `sum(rate(http_requests_total{status=~"5.."}[5m]))`. Para el volumen HTTP, los rechazos, el score y la disponibilidad se consultaron `sum by (status) (http_requests_total{route="/predict"})`, `http_requests_total{route="/predict",status="422"}`, `ml_prediction_score_bucket` y `up{job="ml-api"}`.
- **Limitación.** La consulta 5xx produjo un vector vacío porque el tráfico de laboratorio no generó series 5xx. La tasa y el p95 describen una muestra breve de demostración. [Configuración de scrape](../prometheus/prometheus.yml) · [Servicios y volumen](../compose.yaml)
